# 自定义工具箱应用设计说明书

> 版本：v1.2
> 最后更新：2026-05-01
> 适用范围：Windows 桌面端小工具应用
> 产品形态：插件化、本地优先、极简工具型桌面应用
> 设计基准：当前已实现的插件注册、统一调用、结构化日志、Web UI 工具列表与工具详情页，以及 6 个内置工具能力边界，均以项目架构文档为准。

---

## 1. 文档目标

本文档用于统一整个应用的产品设计、交互设计、视觉设计和界面结构，作为后续 UI 设计、前端实现与插件扩展的共同基线。

本文档解决以下问题：

- 应用整体应呈现什么样的界面气质
- Windows 桌面端小工具应遵循哪些界面原则
- 主窗口、工具列表、工具详情、状态反馈等部分应如何组织
- 窗口尺寸变化时，各个区域应如何自适应伸缩与换行
- 新增插件时应如何保持一致的体验
- 当前内置工具应如何在统一设计系统下落地

---

## 2. 产品定位

### 2.1 产品定义

自定义工具箱是一个 **Windows 桌面端插件化小工具应用**。  
它的目标不是做成内容平台、官网展示页或视觉化营销产品，而是把零散脚本和高频小能力收敛为一个统一、稳定、可扩展、可追踪的本地工具工作台。

### 2.2 核心价值

- 把零散脚本沉淀为可复用工具
- 通过插件机制降低新增功能成本
- 通过统一调用入口保持前后端一致
- 通过结构化日志提升可维护性与可追踪性
- 通过统一 UI 降低工具使用门槛

### 2.3 当前产品边界

基于架构文档，当前应用已经具备以下产品与技术基础：

- 插件自动发现与自动注册
- 统一调用入口：`invokeTool(tool_id, action, payload)`
- 结构化日志系统
- Web UI 工具列表与工具详情页
- 当前内置工具包括 `sleep_control`、`batch_rename`、`clipboard_history`、`format_validator`、`keygen_tool`、`time_converter`

## 3. 设计总原则

### 3.1 Windows 原生感优先

界面应优先呈现“Windows 桌面工具”的感受，而不是网页、SaaS 营销站或设计作品集。  
具体表现为：

- 视觉安静
- 操作明确
- 层级克制
- 装饰极少
- 不依赖大面积视觉包装

### 3.2 工具效率优先于品牌表达

设计目标是提升使用效率，而不是增加“设计感”。  
任何装饰性元素都不能影响这四件事：

- 看懂当前工具
- 找到需要输入的内容
- 找到主操作按钮
- 看清返回结果与状态

### 3.3 一个区域只承担一种职责

页面应尽量避免混合职责。  
每个区域必须一眼知道作用：

- 顶部栏：全局入口
- 左侧栏：工具切换
- 主工作区：当前工具操作
- 底部状态栏：轻提示与执行反馈

### 3.4 一个页面只保留必要信息

桌面端小工具不需要营销文案、长篇说明和复杂内容模块。  
默认规则：

- 一句说明优于三段解释
- 一个主按钮优于多个并列主按钮
- 一个结果区优于分散反馈
- 一套统一布局优于每个工具都重新设计

### 3.5 统一框架下允许工具差异

所有工具页面共享统一布局和交互模式。  
具体工具只在以下层面变化：

- 输入控件种类
- 主按钮文字
- 结果区内容
- 是否存在预览、清空、复制等次级操作

### 3.6 自适应优先

应用必须在窗口拉伸、缩小、最大化后保持界面平衡。  
不允许出现“主工作区已经变宽，但内部卡片仍保持窄固定宽度并悬空在左侧”的情况。

具体要求：

- 外层容器使用弹性布局而不是固定像素定位
- 主工作区始终占满除侧边栏外的剩余空间
- 输入区、操作区、结果区默认宽度为 `100%`
- 操作按钮、表单项和结果项必须在窄宽度下自动换行或纵向堆叠
- 宽窗口下允许内容区扩展，但要设置可读性上限，避免一行过长

## 4. 目标用户与使用场景

### 4.1 目标用户

- 个人开发者
- 内部工具使用者
- 有脚本沉淀需求的技术人员
- 需要高频使用小功能的办公用户

### 4.2 核心场景

- 批量重命名文件
- 格式化或校验 JSON / YAML
- 管理剪贴板文本
- 生成密码、UUID、Token、Hash
- 执行定时休眠相关操作

### 4.3 非目标场景

当前不追求：

- 内容平台式浏览体验
- 复杂协作系统
- 多人云端工作流
- 大而全平台门户式首页
- 强运营或强品牌视觉包装

## 5. 信息架构

## 5.1 应用结构

整个应用采用单主窗口结构，围绕“工具切换 + 工具操作”展开。

```text
主窗口
├─ 顶部栏
│  ├─ 应用名
│  ├─ 搜索框
│  └─ 设置入口
├─ 左侧工具列表
│  ├─ 分类（可选）
│  └─ 工具项
├─ 右侧工具工作区
│  ├─ 工具标题
│  ├─ 简短说明
│  ├─ 输入区
│  ├─ 操作区
│  └─ 结果区
└─ 底部状态栏
   └─ 非阻塞提示 / 状态反馈
```

## 5.2 页面层级

整个应用应尽量控制在两级信息层级内：

- 一级：工具选择
- 二级：工具详情与操作

避免出现过深导航、复杂二级菜单或多层弹窗。

## 6. 总体布局设计

## 6.1 主窗口尺寸建议

### 默认尺寸

- 宽度：1280 px
- 高度：800 px

### 最小尺寸

- 宽度：960 px
- 高度：640 px

### 最大化状态

- 必须正常工作
- 不允许因窗口过宽导致右侧内容区仍保持窄固定宽度
- 主工作区应根据可用空间扩展，区块重新分布，而不是简单留下大片空白

原因：

- 需要容纳左侧工具列表和右侧工作区
- 保证表单、结果区和状态区可同时阅读
- 保证窗口在标准屏与大屏下都保持合理的信息密度

## 6.2 布局比例

- 顶部栏高度：56 px
- 左侧栏宽度：`clamp(200px, 18vw, 256px)`
- 底部状态栏高度：32 px
- 右侧主工作区：剩余空间自适应

说明：

- 左侧栏不建议写死为单一宽度
- 在较宽窗口中，侧栏最多扩展到 256 px
- 在较窄窗口中，侧栏可收缩到 200 px，但不应压缩到影响工具名称识别

## 6.3 布局原则

- 固定左侧导航，保证工具切换稳定
- 右侧主区滚动，不让整个窗口滚动
- 顶部只保留全局能力，不混入当前工具操作
- 底部只显示轻量状态，不承担主要交互
- 所有主内容卡片默认跟随主工作区伸缩

## 6.4 自适应布局总规则

### 外层结构

应用整体应采用 `flex` 或 `grid` 实现弹性布局：

```css
.app-shell {
  display: flex;
  width: 100%;
  height: 100%;
  min-width: 960px;
  min-height: 640px;
}

.sidebar {
  flex: 0 0 clamp(200px, 18vw, 256px);
}

.workspace {
  flex: 1 1 auto;
  min-width: 0;
  display: flex;
  flex-direction: column;
}
```

关键点：

- `workspace` 必须设置 `min-width: 0`，否则内部内容容易溢出
- 左右两栏必须是弹性关系，而不是绝对定位
- 主工作区必须真正占满剩余宽度

### 右侧主工作区

右侧工作区应分为两层：

1. **工作区外层**：负责占满剩余空间
2. **内容容器内层**：负责控制可读宽度、内边距和区块排列

推荐规则：

```css
.workspace-scroll {
  flex: 1 1 auto;
  overflow: auto;
}

.tool-page {
  width: 100%;
  max-width: 1360px;
  margin: 0 auto;
  padding: 24px 28px 32px;
  box-sizing: border-box;
}

.section-card {
  width: 100%;
  box-sizing: border-box;
}
```

这意味着：

- 内容区不能再写死成 840 px、900 px 这类固定宽度
- 区块在正常桌面窗口下应横向拉伸
- 在超宽屏下可以通过 `max-width` 控制阅读舒适度
- 视觉上允许留白，但留白必须是“收敛后的平衡留白”，不是“内容没有跟着窗口变宽”

## 6.5 宽度分档规则

### A. 宽窗口（≥ 1440 px）

目标：充分利用空间，但不让信息摊得太散。

规则：

- 主内容容器可扩展至 `max-width`
- 表单项可采用双列或自适应多列
- 结果区可拆为两列信息块
- 操作按钮维持一行显示，必要时右对齐或左对齐分组

### B. 标准窗口（1100–1439 px）

目标：保持当前主视图的稳定性。

规则：

- 页面区块单列为主
- 表单内部可用 `auto-fit` 做 1–2 列弹性排列
- 操作区横向排列，但必须允许换行
- 结果区使用一列，局部指标可以 2 列

### C. 紧凑窗口（960–1099 px）

目标：保证功能可用，不出现拥挤和溢出。

规则：

- 左侧栏收窄至最小宽度
- 主区统一单列
- 输入控件纵向堆叠
- 操作按钮自动换行
- 较长的结果项允许换行或滚动

## 6.6 组件自适应规则

### 顶部栏

- 搜索框宽度使用区间值：`clamp(240px, 36vw, 560px)`
- 设置按钮靠右，不写死大宽度
- 顶部栏内元素通过 `gap` 控制间距，而不是固定空白占位

### 左侧工具栏

- 工具项宽度跟随侧栏
- 名称超长时省略，不允许挤压图标
- 在紧凑窗口下仍保持“图标 + 名称”可读，不切成不完整布局

### 输入区

- 输入面板宽度始终为 `100%`
- 面板内部采用弹性网格：

```css
.form-grid {
  display: grid;
  grid-template-columns: repeat(auto-fit, minmax(280px, 1fr));
  gap: 16px;
}
```

- 单字段页面也应让输入框随面板拉伸，而不是只占固定窄宽度

### 操作区

- 按钮组使用横向 `flex` + `wrap`
- 一个主按钮，多个次按钮时允许自动换行
- 不允许按钮因为窗口缩小而溢出卡片边界

```css
.action-row {
  display: flex;
  flex-wrap: wrap;
  gap: 12px;
}
```

### 结果区

- 结果区默认宽度为 `100%`
- 结果摘要类内容可自适应分列
- 长文本结果应提供滚动、换行或复制，而不是撑破布局

```css
.result-grid {
  display: grid;
  grid-template-columns: repeat(auto-fit, minmax(240px, 1fr));
  gap: 12px;
}
```

## 6.7 针对当前问题的修正规则

针对截图中“窗口已很宽，但输入区、操作区、结果区仍然只占左侧一小块”的问题，明确增加以下约束：

- 禁止在主工作区内部使用写死像素宽度的卡片容器
- 禁止输入区、操作区、结果区依赖固定 `width` 或绝对定位
- 禁止仅扩大外层工作区，而不让内层内容容器同步扩展
- 当窗口横向变宽时，主内容容器必须先扩展到合理上限，再决定是否保留留白
- 当窗口横向缩小时，按钮、表单和结果项必须优先换行，而不是溢出或压缩到不可读

## 6.8 推荐实现方式

推荐布局链路：

```text
主窗口
→ AppShell（横向 Flex）
  → Sidebar（宽度区间固定）
  → Workspace（占满剩余空间）
    → ScrollArea（负责滚动）
      → ToolPage（100% 宽 + max-width + padding）
        → SectionCard（100% 宽）
          → FormGrid / ActionRow / ResultGrid（自适应布局）
```

这套规则的目标不是把界面做成网页响应式站点，而是保证桌面工具在常见窗口尺寸下都保持：

- 结构稳定
- 组件可读
- 空间被合理利用
- 不出现明显的悬空和浪费

## 7. 视觉设计系统

## 7.1 视觉关键词

- 极简
- 安静
- 克制
- 明确
- 稳定
- 可信
- 接近系统工具

## 7.2 色彩系统

### 基础色

- 页面背景：`#F5F6F8`
- 面板背景：`#FFFFFF`
- 一级文字：`#1F2328`
- 二级文字：`#667085`
- 占位文字：`#98A2B3`
- 边框：`#E5E7EB`
- 分隔线：`#ECEFF3`

### 主题色

- 主色：`#2563EB`
- 主色悬停：`#1D4ED8`
- 主色浅底：`#EFF6FF`

### 状态色

- 成功：`#16A34A`
- 成功浅底：`#F0FDF4`
- 警告：`#D97706`
- 警告浅底：`#FFFBEB`

- 错误浅底：`#FEF2F2`

## 7.3 圆角系统

- 小控件：8 px
- 按钮：8 px
- 输入框：8 px
- 卡片：10 px
- 弹层：12 px

原则：  
不使用大圆角，不做卡片感过强的网页式圆角。

## 7.4 阴影系统

默认尽量少用阴影，优先用边框分层。

### 标准阴影

```css
box-shadow: 0 4px 16px rgba(15, 23, 42, 0.06);
```

适用范围：

- 弹出层
- 下拉面板
- 轻浮层

普通卡片和内容面板可以无阴影，仅用边框。

## 7.5 字体系统

建议采用系统默认字体或接近 Windows 原生字体体系。

### 字号建议

- 窗口主标题：20 / 28 / 600
- 区块标题：16 / 24 / 600
- 正文：14 / 22 / 400
- 辅助说明：13 / 20 / 400
- 标签文字：12 / 18 / 500

原则：

- 不使用过大的营销式标题
- 以正文可读性优先
- 标题层级尽量少

## 7.6 间距系统

建议使用 4 的倍数体系：

- 4
- 8
- 12
- 16
- 20
- 24
- 32

主要规则：

- 控件内部 padding 以 8 / 12 / 16 为主
- 模块之间间距以 16 / 24 为主
- 大区块上下间距以 24 / 32 为主

## 8. 组件设计规范

## 8.1 顶部栏

### 结构

- 左：应用图标 + 应用名
- 中：全局搜索
- 右：设置按钮

### 样式

- 高度固定 56 px
- 白底
- 下边框 1 px
- 不使用毛玻璃与重阴影

### 行为

- 搜索支持按工具名筛选
- 设置按钮打开全局设置弹层或独立页
- 顶部栏不承载具体工具操作

## 8.2 左侧工具列表

### 每个工具项包含

- 图标
- 名称
- 选中态背景

### 样式

- 列表项高度：40–44 px
- 水平内边距：12–14 px
- 选中项使用主色浅底 + 主色文字
- hover 使用浅灰底

### 规则

- 不使用复杂卡片
- 不显示过多描述
- 名称最多一行，超出省略
- 图标统一线性风格

## 8.3 页面标题区

### 内容

- 工具标题
- 一句简短说明

### 规则

- 标题不超过 14 个汉字或 24 个英文字符
- 说明不超过两行
- 说明只表达工具用途，不写教程

示例：

- 批量重命名  
  预览并执行文件重命名，自动检查冲突。

## 8.4 输入控件

### 文本输入框

- 高度：36 px
- 圆角：8 px
- 边框：1 px
- focus 时主色描边

### 多行输入框

- 最小高度：120 px
- 支持滚动
- 用于 JSON / YAML 等大块文本输入

### 路径选择器

- 文本框 + 浏览按钮组合
- 浏览按钮固定宽度
- 不使用复杂文件树嵌入

### 开关与复选框

- 仅用于明确布尔参数
- 每个区块内最多 3–5 项，避免表单过重

## 8.5 按钮

### 主按钮

- 一个页面只允许一个主按钮
- 主色填充
- 白字
- 高度：36 px
- 最小宽度：96 px

### 次按钮

- 白底描边
- 用于清空、取消、复制、导出等次级操作

### 危险按钮

- 仅在删除、清空历史、立即休眠等高风险动作中使用
- 默认不高亮，需通过文案明确风险

## 8.6 结果区

### 结果区职责

- 呈现工具执行结果
- 提供复制、保存、清空等后续操作
- 显示执行成功或失败

### 样式

- 与输入区分离
- 使用白底面板
- 顶部可有结果标题与状态标识
- 结果文本允许选择和复制

### 行为

- 成功结果显示绿色状态条或标记
- 错误结果显示红色状态条或标记
- 支持一键复制结果
- 有历史上下文时应明确当前结果属于哪次操作

## 8.7 Toast / 状态提示

### 用途

- 非阻塞反馈
- 操作已完成
- 操作失败
- 风险提示

### 规则

- 出现于右下或底部状态栏附近
- 文案简短
- 自动消失
- 不影响主操作流程

## 8.8 状态栏

### 内容

- 当前系统状态
- 最近一次执行状态
- 轻提示

### 示例

- 就绪
- 已生成 1 个 UUID
- 重命名已执行
- JSON 校验失败

状态栏不承载确认、表单或复杂通知。

---

## 9. 交互设计原则

## 9.1 主路径最短

每个工具的首要操作路径应尽量收敛为：

1. 输入必要内容
2. 点击主按钮
3. 在结果区看到反馈
4. 如有需要再复制或清空

## 9.2 减少不必要弹窗

只有在以下场景使用确认弹窗：

- 高风险动作
- 不可逆动作
- 会影响系统状态的动作

例如：

- `sleep_now`
- `clear`
- 真正执行批量重命名
- 删除剪贴板历史项

## 9.3 先预览再执行

对具有破坏性的操作，优先采用“两步式”交互：

- 第一步：预览
- 第二步：确认执行

这尤其适用于 `batch_rename`，也与当前能力边界一致。

## 9.4 反馈必须贴近动作发生点

- 输入校验错误：显示在输入区附近
- 操作成功：显示在结果区和状态栏
- 全局系统问题：显示 Toast 或状态栏
- 不要把错误只写进日志而不反馈给用户

## 9.5 风险可见

涉及系统动作、清空操作或覆盖写入时，必须显式表达风险：

- 使用更明确文案
- 使用警告色
- 必要时要求再次确认

---

## 10. 工具页统一模板

每个工具详情页必须遵循统一模板：

```text
[工具标题]
[一句说明]

[输入区]
- 必要输入控件
- 可选参数控件

[操作区]
- 一个主按钮
- 0~3 个次按钮

[结果区]
- 执行结果
- 复制 / 清空 / 导出
```

### 模板约束

- 不出现多列复杂布局
- 不在一个工具页中嵌套多个复杂面板
- 不使用多层页签
- 不出现超过两个主要视觉焦点

---

## 11. 内置工具详细设计

## 11.1 Sleep Control

### 定位

执行与系统休眠相关的快捷操作。

### 页面结构

- 倒计时时长输入
- 开始倒计时按钮
- 取消计划按钮
- 立即休眠按钮
- 当前计划状态显示

### 设计重点

- `sleep_now` 属于高风险动作，应显式确认
- 倒计时状态需持续可见
- 取消操作应始终可达

### 反馈

- 已开始倒计时
- 已取消计划
- 系统即将休眠 / 已执行

当前支持的动作包括 `start_countdown`、`cancel_plan`、`sleep_now`。

## 11.2 Batch Rename

### 定位

批量预览并执行文件重命名。

### 页面结构

- 目标目录选择
- 重命名规则输入
- 预览按钮
- 应用按钮
- 清空预览按钮
- 预览列表 / 差异列表

### 设计重点

- 默认强调“预览”
- `apply` 仅在预览完成后可点
- 冲突文件必须高亮
- 每个改名项应显示“原名 → 新名”

### 反馈

- 预览成功
- 存在冲突
- 已执行重命名
- 无可执行项目

当前支持的动作包括 `preview`、`apply`、`clear_preview`。

## 11.3 Clipboard History

### 定位

自动捕获和管理系统剪贴板文本。

### 页面结构

- 历史列表
- 置顶 / 取消置顶
- 复制回剪贴板
- 删除单项
- 清空全部

### 设计重点

- 列表可快速扫描
- 文本预览不宜过长
- 置顶项应明显区分
- 复制操作应一键可达

### 反馈

- 已复制到剪贴板
- 已置顶
- 已删除
- 已清空

当前支持的动作包括 `set_clipboard`、`toggle_pin`、`remove_item`、`clear`，并支持自动捕获文本剪贴板。

## 11.4 Format Validator

### 定位

对 JSON / YAML 进行格式化或校验。

### 页面结构

- 输入文本区
- 格式类型选择
- 处理按钮
- 清空按钮
- 输出结果区
- 错误信息区

### 设计重点

- 输入区与输出区应清晰分开
- 校验失败时显示可理解错误
- 成功时支持一键复制格式化结果
- 不要把错误只展示为技术堆栈

### 反馈

- 格式正确
- 已格式化
- 第 N 行格式错误

当前支持的动作包括 `process`、`clear`，适用于 JSON / YAML 的格式化与校验。

## 11.5 Keygen Tool

### 定位

生成密码、Token、UUID，或对文本/文件执行哈希。

### 页面结构

- 生成功能切换区
- 参数设置区
- 哈希文本输入区
- 哈希文件选择区
- 生成按钮
- 输出结果区
- 复制按钮
- 清空按钮

### 设计重点

- 每种生成模式共享同一布局
- 参数区根据模式切换，但页面骨架不变
- 哈希模式中，文件输入优先级高于文本输入
- 文件哈希需要显示文件名和大小，避免用户误判当前输入源
- 输出结果默认可复制
- 敏感结果需要注意可见性和清理方式

### 反馈

- 已生成密码
- 已生成 Token
- 已生成 UUID
- 文本哈希完成
- 文件哈希完成

当前支持的动作包括 `generate_password`、`generate_token`、`generate_uuid`、`hash_text`、`hash_file`、`clear`。

## 11.6 Time Converter

### 定位

在秒/毫秒时间戳与本地/UTC 时间之间双向转换。

### 页面结构

- 转换方向选择
- 时间戳单位选择
- 无时区输入解释方式
- 输入值文本区
- 转换按钮
- 填充当前时间按钮
- 清空按钮
- 本地时间、UTC 时间、秒时间戳、毫秒时间戳结果区

### 设计重点

- 不使用原生 `select`，避免 Qt WebEngine 下拉菜单出现白框与渲染不一致问题
- 时间戳单位需要支持自动识别、秒、毫秒
- 当前时间展示应与转换结果分区，避免用户误把 Now 当作输入结果
- 时间字符串应清晰区分本地时间和 UTC 时间

### 反馈

- 转换完成
- 当前时间已填充
- 输入为空或格式错误

当前支持的动作包括 `now`、`convert`、`clear`。

## 12. 搜索与发现设计

## 12.1 搜索目标

搜索仅用于快速定位工具，不承担全局内容搜索职责。

## 12.2 搜索范围

- 工具名
- 工具 summary
- 可选：动作关键词

## 12.3 设计要求

- 搜索框放在顶部栏中央
- 输入时即时过滤左侧工具列表
- 搜索为空时恢复完整列表
- 结果为空时显示简短空状态

---

## 13. 设置页设计

## 13.1 设置页定位

设置页只管理全局偏好、运行状态与应用级行为，不承载工具本身功能。

## 13.2 建议内容

- 运行概览：应用名、Python 版本、系统平台、插件数量、日志文件规模
- 本地目录：工作空间、`.data`、日志目录、`.qtwebengine`
- uv 环境：`UV_CACHE_DIR`、`UV_TOOL_DIR`、`UV_PYTHON_INSTALL_DIR`
- 插件清单：当前自动注册的工具与摘要
- 加载错误：插件扫描或加载失败信息
- 最近日志：最近运行事件摘要
- 后续可扩展：主题模式、日志保留策略、默认窗口行为、启动行为

## 13.3 设计原则

- 设置项分组明确
- 不过度复杂
- 不引入大量二级设置页
- 风险项单独分区
- 当前阶段以只读状态中心为主，避免提供没有后端支撑的伪设置

---

## 14. 空状态、错误状态与边界状态

## 14.1 空状态

适用场景：

- 没有搜索结果
- 没有预览内容
- 剪贴板历史为空
- 尚未执行任何操作

文案规则：

- 简短
- 明确下一步操作
- 不写营销性语言

示例：

- 暂无可显示结果
- 请输入内容后开始处理
- 还没有剪贴板记录

## 14.2 错误状态

错误信息必须做到：

- 可理解
- 可定位
- 不吓人
- 不只显示堆栈

错误文案结构建议：

```text
操作失败
原因：目标目录不存在
建议：请重新选择目录后再试
```

## 14.3 禁用状态

在以下场景中，主按钮应禁用：

- 必填项为空
- 预览未完成但要求执行
- 当前存在阻塞性错误
- 正在执行且不允许重复提交

---

## 15. 动效与过渡

## 15.1 总原则

动效必须非常克制。  
它的作用只是帮助理解状态变化，不是制造视觉存在感。

## 15.2 推荐动效

- hover 背景色渐变：120–160ms
- 按钮按下反馈：80–120ms
- Toast 淡入淡出：160–200ms
- 面板出现：轻微 opacity + translateY

## 15.3 禁止事项

- 大幅位移动画
- 夸张弹跳
- 渐变流光
- 连续背景动效
- 会干扰工具使用的视觉特效

---

## 16. 可访问性与可用性

## 16.1 可读性

- 正文最小字号不低于 13
- 前景文字与背景保持足够对比
- 错误与成功不能只依赖颜色，还要有文案或图标

## 16.2 键盘操作

关键路径应支持键盘：

- 搜索框聚焦
- 左侧列表上下切换
- 表单 tab 切换
- Enter 触发主操作
- Esc 关闭弹层

## 16.3 可复制性

所有结果型内容都应优先支持复制。  
尤其是：

- 格式化结果
- UUID / Token / 密码
- 哈希结果
- 剪贴板内容

---

## 17. 与现有架构的对齐要求

设计不是独立于架构存在的。  
界面设计必须围绕现有系统能力展开。

## 17.1 插件系统对齐

由于应用采用 manifest 扫描与动态导入插件入口，因此 UI 层应默认支持：

- 工具列表的动态扩展
- 工具详情页的统一容器
- 工具状态导出与恢复
- 加载失败状态展示

## 17.2 统一调用对齐

由于操作通过统一入口 `invokeTool(tool_id, action, payload)` 执行，因此前端交互建议统一为：

- 收集输入
- 组装 payload
- 执行动作
- 接收统一返回结构
- 更新结果区与状态区

## 17.3 日志系统对齐

对于关键动作，应在交互层体现“可追踪”理念：

- 成功与失败明确反馈
- 风险动作明确确认
- 错误不被静默吞掉
- 重要结果可回看

以上均与当前架构设计一致。

---

## 18. 后续扩展设计要求

未来新增插件时，必须遵循以下设计约束：

### 18.1 不破坏主框架

- 不新增新的主窗口结构
- 不把单个插件做成独立系统
- 不引入特殊导航体系

### 18.2 复用统一模板

- 标题区
- 输入区
- 操作区
- 结果区

### 18.3 复用统一状态模型

- idle
- loading
- success
- error
- empty

### 18.4 复用统一按钮层级

- 一个主按钮
- 有限次按钮
- 高风险按钮单独处理

---

## 19. 不应采用的设计方向

以下方向明确不建议采用：

- 官网式 Hero 首屏
- 大面积品牌渐变
- 过度圆角和厚重阴影
- 插画型内容主导界面
- 每个工具都做不同风格
- 强营销文案与内容运营模块
- 网页化多段长页面结构
- 把桌面工具做成卡片流内容平台

原因很简单：  
这些方向会削弱“工具性”，提升学习成本，并让整个应用失去 Windows 桌面端小工具应有的轻量和明确。

---

## 20. 结论

整个应用的正确设计方向应当是：

**一个本地优先、插件化、结构清晰、可扩展的 Windows 极简工具工作台。**

它应具备以下特征：

- 像工具，而不是像官网
- 像系统应用，而不是像网页模板
- 以操作效率为第一优先
- 以统一框架承载不同工具能力
- 在保持克制的前提下具备稳定、可信的产品质感

这套设计既符合桌面端小工具的使用心智，也能与当前的插件注册、统一调用、结构化日志和内置工具能力自然对齐。
